## Findings, most severe first

### 1. [MEDIUM] `agentRuntime/runtime.ts` dispatches every READ tool with a hardcoded empty auth token — silently breaks the moment a tool needs it, and the ADR-006 "same trust boundary" claim isn't fully true

`server/src/services/agentRuntime/runtime.ts`, inside the tool-call handler:

```ts
const result = await toolRegistry.dispatch(identity, call.name, call.args, { rawToken: "" });
```

Compare `server/src/routes/agentGateway.ts` (the existing, live Arena gateway route), which does
the equivalent dispatch with the *real* verified token:

```ts
const rawToken = req.serviceToken!;
...
const result = await toolRegistry.dispatch(identity, call.name, call.args, { rawToken });
```

`ToolExecutionContext.rawToken` exists specifically so a tool can "call back into its own
product's authenticated API... forwards this same token as its own Authorization header"
(`server/src/services/tools/productConnector.ts`'s own doc comment). `startRun()`'s signature —
`startRun(identity, goal, budget)` — never accepts a token at all, so there is no way for any
future caller to plumb a real one through even if it wanted to.

**Why this doesn't fail today:** none of the 4 registered Arena READ tools
(`search`/`nearbyActivities`/`listCommunities`/`searchJobs`, all plain unauthenticated
`arenaGet()` calls) or the 2-3 `jennysol.*` tools read `context.rawToken`. And `startRun()` isn't
wired into any HTTP route yet (`grep -rn "startRun" server/src/routes/` returns nothing) — it's
only reachable from `runtime.test.ts` and the eval script, so this can't be hit by a real user
right now.

**Why it's still worth fixing before this ships further:** it's a structural gap, not a coverage
gap — no amount of adding tests today would catch it, because no current tool exercises the path.
The moment anyone adds a READ tool that needs real Arena auth (e.g. "list my own applications" or
anything scoped to the calling user rather than public data), it will either silently send
`Authorization: Bearer ` (empty) and get a confusing 401 from Arena's
`AgentServiceTokenAuthenticationFilter`, or — worse, if that filter is ever loosened — succeed as
an unintended anonymous/wrong-identity call. It also means ADR-006's claim that `AgentGoalRun`
"uses...exactly the same trust boundary the live Arena gateway already uses" overstates the
current state: the tool-registry/scope half of that boundary is shared, but the token-forwarding
half was never wired through.

**Recommendation:** thread a real token (or explicitly document that `AgentGoalRun` is
token-less-by-design and restrict it to tools proven not to need one, enforced at registration
time) before wiring `startRun()` to any route, and add a test that fails if a tool needing
`rawToken` is ever dispatched through a Goal Run with an empty one.

### 2. [MEDIUM] A WRITE tool call inside a paused run isn't guarded against being proposed twice — two independently-approvable real actions can result from what looks like one pause

Same file, WRITE-tier branch. When a WRITE tool call comes in, `proposeAction()` creates a new
pending action and the run's `pendingActionId` is overwritten with it — but the model's turn is
deliberately **not aborted** (a documented, reasonable choice, so the model can say "awaiting your
approval" in its own words). The comment in the code itself already flags the risk:

```ts
// (Known simplification: if a run proposes a SECOND action before finishing,
// only the latest one is tracked as this run's pendingActionId — good enough
// for a first cut, not a claim that concurrent multi-approval runs are solved.)
```

What this means concretely: if the model, having just been told "awaiting_user_approval," decides
(within the same turn, before the loop returns) to call the same or a different WRITE tool again
— e.g. misreading the pause as a failure and retrying — `proposeAction()` runs a second time. The
budget guard (`stepIndex >= maxSteps`) does not prevent this as long as steps remain. The result:
**two live, independently-approvable `PendingAction` rows exist** (each single-use, each really
executable via `/api/agent/gateway/actions/:id`), but the run object only ever exposes the second
one via `pendingActionId`. The first is orphaned from the run's point of view but not from
`pendingActions.ts`'s — anyone who still has its id (e.g. a client that read `pendingActionId`
before the overwrite, or a UI that lists all pending actions rather than trusting the run) could
approve it too, causing a second real-world side effect (e.g. joining an activity twice, or two
job applications) that the run itself has no record of ever having proposed.

This is **not** double-execution of the *same* action (that path is airtight — `consumeAction()`
deletes the row transactionally before returning it, so a given `actionId` can only ever be
approved once). It's a double-*proposal* gap: nothing stops a run from creating two live
real-world-executable proposals when the design intends one pause = one proposal.

**Not covered by any test.** `runtime.test.ts`'s WRITE-tier test only exercises a single tool
call. No test asserts what happens on a second WRITE call within the same run.

**Recommendation:** either abort/short-circuit the model's turn once `awaiting_approval` is
reached (accepting the "aborts the model's own natural continuation" tradeoff the current comment
argues against), or explicitly reject/expire the first pending action when a second one is
proposed by the same run, and add a test pinning whichever behavior is chosen.

### 3. [LOW, unconfirmed] Possible TOCTOU on the step-budget check under parallel tool calls

```ts
if (stepIndex >= run.budget.maxSteps || Date.now() - startedAt >= run.budget.maxMs) { ... }
const index = stepIndex++;
```

This check-then-increment is only atomic if the underlying provider always awaits one tool-call
callback before invoking the next. I did not find anywhere in `modelRouter.ts`/`llmProvider.ts`
that documents whether tool calls are ever dispatched in parallel (some LLM providers do support
parallel tool calls in one turn). If they ever are, two callbacks could both pass the `stepIndex
>= maxSteps` check before either increments it, letting the budget be exceeded by more than the
one documented "one more sneaks in" case the comment explicitly guards against. I'm flagging this
as **plausible, not confirmed** — I did not have budget in this review to trace every provider's
tool-call dispatch path exhaustively. Worth a targeted look, and a test that calls the handler
concurrently (`Promise.all`) rather than only sequentially (as every existing test does).

### 5. [INFO — confirmed real, but already honestly self-disclosed] No approval-continuation link back to the run

Once a Goal Run's WRITE tool is approved via the pre-existing
`/api/agent/gateway/actions/:id` route, nothing updates `agent_goal_runs` — I confirmed
`agentGateway.ts` contains zero references to `agentRuntime`, `getOwnedRun`, or `updateRun`. A
run that reaches `awaiting_approval` stays in that status forever in the database, with no
recorded link between the approved action's real-world result and the run's own completion state.
This exactly matches what `JENNYSOL-ARCHITECTURE.md` §8 ("no...approval continuation yet"),
`PROGRESS.md`, and `BLOCKERS.md` already say, so it's not a hidden gap — but it's real, I verified
it directly rather than taking the doc's word for it, and it means `AgentGoalRun.status` cannot be
trusted as a UI-facing "did this actually finish" signal yet. Don't build a dashboard against it
before this is closed.

## What I checked and found solid (no finding)

- **Ownership/IDOR:** `getOwnedRun()` (`agentRuntime/store.ts`) and `consumeAction()`
  (`tools/pendingActions.ts`) both compare `product` + `externalUserId` + `tenantId` before
  returning a row — the same three-field convention, applied consistently. `stopRun()` correctly
  refuses (`"No such run"`, not a different error) when called with a non-owning identity, proven
  by a real test (`runtime.test.ts`, "stopRun on an identity that doesn't own the run refuses").
- **Cross-product tool isolation:** enforced independently at both `getToolsFor()` (what the model
  is even offered) and `dispatch()` (`CrossProductToolAccessError` if the tool's namespace prefix
  doesn't match the caller's product) — belt and suspenders, proven by a real test that inspects
  the actual tool list passed to `routeChatCompletion`, not just the registry's stated intent.
- **SQL injection / schema:** every new query in `store.ts`/`vectorStore.ts` is a parameterized
  `db.prepare(...).run(...)`/`.get(...)`/`.all(...)` call — no string concatenation anywhere.
  `agent_goal_run_steps.run_id` has a proper `REFERENCES agent_goal_runs(id) ON DELETE CASCADE`.
  New tables are additive (`CREATE TABLE IF NOT EXISTS`) — no migration/rollback risk to existing
  tables.
- **Memory export/delete scoping** (`documents.ts`, `vectorStore.ts`): both new routes and both
  new store functions filter by `user_id` in the query itself (never post-filtered), matching
  every existing function in the file. Route ordering is safe — `GET /export` and `DELETE /` don't
  collide with the pre-existing `DELETE /:id` (Express only matches `:id` against a real path
  segment, and no `GET /:id` route exists to shadow `/export`).
- **ADR-006's core claim, re-derived independently, not trusted from its own text:**
  `agentSessionStore.ts`/`agentScheduler.ts`/`agentSessionRunner.ts`/`agentToolRegistry.ts` are
  real, wired-in, and genuinely use a *different* tool registry
  (`agentToolRegistry.ts`, keyed by `(sessionId, agentId)` + a permissions field) than the product
  `ToolRegistry` `AgentGoalRun` uses — confirmed by reading `agentToolRegistry.ts` directly, which
  explicitly does not import or extend `toolRegistry.ts`/`pendingActions.ts`. The three concepts
  really are non-redundant on inspection, not just by the ADR's own assertion.
- **`arena.test.ts`'s new risk-table contract-lock test** and **`agentGateway.http.test.ts`'s new
  forged-token and HTTP-level-TTL tests** are real behavioral tests (a genuinely forged JWT through
  the real Express app, a genuinely advanced fake clock past the real 5-minute TTL) — not mirrors
  of the implementation.
- **`keepWarm.ts`'s STEP 3 change** is a correctly-scoped, opt-in, off-by-default addition; nothing
  in it runs unless `OLLAMA_KEEP_WARM_CAPABILITIES` is explicitly set.
- Diff scope: no file outside `jennysol-ai` touched, no Arena repo edits, no `SERVICE_TOKEN_SECRET_ARENA`
  rotation, nothing that would require Cursor/Arena-side changes (`JENNY-ARENA-CONTRACT.md` §6,
  proposed additions, is still empty, consistent with the report's own claim).
